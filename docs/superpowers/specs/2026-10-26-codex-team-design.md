# 统一终端 AI 小组设计

## 用户需求与使用方式

用户已确认统一终端，并澄清目标是效率、能力与正确率的综合提升，而非固定“一人执行、一人检查”。进入任意项目目录运行 `team`，任务和补充进入双方共享聊天，由成员协商最小合理计划：简单任务可单人完成且不另行检查，复杂任务可拆分并行，检查按风险与实际需要安排；同一项子任务只有一个负责人，角色随任务变化。

## 已确认的环境

- WSL Ubuntu，Bash，Python 3.14.4，Codex CLI 0.164.0。
- GPT 复用 `~/.codex/config.toml` 的模型设置和现有 Codex 登录。
- DeepSeek 复用 `~/.codex/deepseek-menu.config.toml`，当前模型为 `deepseek-flash`，提供商为 `deepseek-menu`。
- DeepSeek 密钥按现有菜单方式读取：`DEEPSEEK_API_KEY` 环境变量优先，其次 `~/.local/share/codex-menu/credentials.json`。从不输出密钥或把它放入进程参数。
- 本机 Codex 已提供 app-server 和本机生成的协议 schema；模型连通性尚未进行付费请求验证。
- 当前工作区已有其他任务的未提交修改；本工具只新增自己的源文件和文档，不修改或提交既有工作。

## 方案取舍

1. **统一终端 + 两个 Codex app-server 进程（采用）**：复用用户现有模型配置、登录、文件与命令工具；需要实现消息转发、任务调度及终端界面。用户已选择新增终端命令这一入口形式；采用 app-server 是实现方的建议。
2. 直接用通用多 Agent 框架调用模型 API：群聊抽象现成，但需要另行配置模型客户端、实现代码操作工具，以及核实 GPT 的 API 凭据。
3. 修改 Codex 自带终端：需要维护自定义客户端，超出新增统一入口所需范围。

## 第一版行为

### 入口与界面

- `team` 在当前目录启动中文终端小组；`team -C <目录>` 可指定项目。
- 只提供一个输入框，不弹出模型选择菜单。成员发言标注来源，方便阅读，但用户无需指定由谁执行。
- 显示公开消息、正在执行的命令、文件修改与完成/失败状态。仅传递公开协作信息，不转发或展示模型的原始内部推理。
- `/help` 查看指令，`/status` 查看两位成员状态，`/stop` 中断本轮双方工作，`/quit` 关闭两个后台进程并退出。Ctrl+C 中断当前任务；EOF 退出。
- 提供 `team --doctor` 检查依赖、配置和凭据是否存在；它不发起模型请求，不能把“已配置”显示成“连通性已验证”。

### 共享聊天与调度

- 两个成员维护各自独立的 Codex 线程，外层保存一份带序号的公共消息记录。
- 用户每次输入都追加到公共记录，并送给双方。执行中的补充通过本机协议支持的 steer/排队方式送达；在下一次模型运行前补齐未读记录。
- 成员可用受运行时支持的协作操作发送消息、提出或接受任务、请求对方复核、报告完成。具体采用动态工具或结构化回合输出，由实现方依据实测协议兼容性决定，不能仅显示模拟群聊。
- 调度器执行成员确认的子任务图，记录负责人、依赖、读写范围、按需检查者、状态和产物。仅传递新增公开消息，避免整段历史反复回灌。
- 独立子任务可以并行；同一成员一次只执行一项。读写范围由计划声明，写入不同且互不包含的目录可以并行；重叠目录的写入排队。后端把每回合工作目录及沙箱写入范围限制到已分配目录。
- 分工可随任务改变，不把“GPT 只规划、DeepSeek 只写代码”写死。
- 双方先简短确认计划，不做重复实施。提案方轮换，另一方可以直接确认或修改计划，不强迫双方各写一份完整方案。
- 每项子任务唯一认领，不为整个用户任务锁定一位执行者。没有分配工作的成员可待命；没有必要时不触发额外检查。
- 成员自行完成必要验证；计划可指定独立检查，执行者也可在发现风险后请求检查。指定检查者保持只读，不能重复实施。
- 失败或能力不匹配时可请求重新协商；已经完成的工作作为进度保留，未完成项允许换人，避免盲目重做。
- 所有必要子任务和已请求的检查完成后才汇总。达到上限或出错时列明未完成事项，不冒充完成。
- 实现方设定一个明确、可配置的讨论/调度回合上限，记录为什么结束，避免成员消息互相触发无限循环。

### 文件、权限和故障

- 使用现有 Codex 工具执行代码任务；讨论、分析和独立检查只读，需要修改的子任务使用限定工作目录的 workspace-write。审批显示来源、内容和范围；不绕过审批或取消沙箱。
- 当前目录含用户未提交修改时，不重置、清理或自动提交这些修改。
- 任一成员启动、认证或请求失败时标出真实错误与成员状态，不显示伪造回复。启动成功不等于模型请求成功；需要一次真实请求才能验证后者。
- `/stop` 清空当前任务的待执行队列，阻止取消前的迟到结果重新启动工作；退出清理子进程并恢复终端。
- 本地会话记录位于用户数据目录，目录权限 0700、文件权限 0600；只记录公开内容与必要事件，不包含凭据。

## 实现范围与交付

- 使用 Python 3.11+，优先标准库，避免引入需要重新安装的大型多 Agent 框架。
- 源码先保存在当前可写工作区 `tools/codex-team/`，与邮件项目现有源码隔离。
- 安装目标是 `~/.local/share/codex-team/` 与 `~/.local/bin/team`；安装不改动现有 `codex` 命令、启动菜单、模型配置或认证文件。卸载保留会话记录。
- 修改用户目录需要在源码、测试及安装内容可审阅后，通过执行工具申请所需文件系统权限。
- 交付包含使用说明、安装/卸载方法、离线自动化验证和实际连通性检查结果。

## 验收

1. 一条用户消息送达两个真实后台会话，双方公开回复显示于同一终端。
2. 一位成员的公开问题或质疑进入另一位成员的下一次上下文，能收到有针对性的回复。
3. 验证简单任务可无额外检查完成，复杂任务可分给双方；独立目录写入可并行，重叠写入排队；模型连通失败如实记录。
4. 后续补充能送达双方，停止和退出不会留下继续写代码的后台任务。
5. 自动化测试覆盖消息顺序和去重、失败重协商、可选检查、依赖与独立并行、写入范围互斥、取消和后续补充、配置复用及终端退出。
6. 安装可重复执行，已有配置、凭据及当前项目修改保持完整。
